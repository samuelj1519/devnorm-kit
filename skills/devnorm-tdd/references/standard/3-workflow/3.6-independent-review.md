# 3.6 Independent review

One non-author primary reviewer independently checks each formal task. Where applicable, review the design, models and test design under section 3.2 before reviewing the candidate. Direct simple tasks need no separate review.

## Review unit and primary reviewer

Fix the objective, specification, standard, author, comparison base and exact candidate. A semantic review unit contains independently assessable behavior, tests, necessary documents and input identity. Review related changes and shared invariants together, even across commits. Verify the final combination separately.

Start in a fresh session uninvolved in implementation. Prefer resuming applicable prior review or the previous round with the original reviewer and session. Check conformance to approved design, test scenarios and assertions. Reviewers only write authorized conclusions and evidence. Replace a reviewer who participates in repairs with a qualified non-author. Preserve handoff reasons and conclusions if independence, trustworthy context or execution conditions are lost.

Check the task record, [review checklist](../1-principles.md#17-manual-review-checklist), complete diff and actual evidence. Record specification and standards conclusions separately. Include committed, staged, unstaged and relevant untracked changes, with exact commits and file hashes. Check for scope violations and inspect gaps in trusted evidence. Check entry points, shared writes, transactions and external effects affecting critical guarantees. Personally run required critical paths. Credit the actual executor of cited evidence. Use [specialized code review](../../methods/code-review/METHOD.md) for effects that cross boundaries or grow unexpectedly.

## Approval and blockers

<!-- devnorm:condition:formal-review-gate:start -->
Approve the exact candidate when it meets applicable mandatory standards, approved design and acceptance criteria and all required verification evidence is present. Missing required independent-review approval or other verification evidence blocks release. When evidence is supplied, check its source and applicability to the exact candidate. Proceed only when all requirements are satisfied.
<!-- devnorm:condition:formal-review-gate:end -->

Applicable violations and failed required checks also block approval. Record the requirement, impact, actual and expected behavior and evidence, or the required evidence missing. Resolve unknowns material to approval. Return confirmed blockers promptly and continue independent investigation within budget.

Style, optional improvements and optional simplification after submission are nonblocking. They require no reply, repair or resubmission. Zero findings is valid. Check automated findings against source and evidence and explain false positives. Authorized owners decide trade-offs and test protection. Safeguard reductions need applicable approval and replacement protection. Approval leaves authorization for later actions separate.

## Incremental re-review and cumulative budget

Prefer the original reviewer for fixes. Check new differences, original issues and affected paths. Replay original failures. Expand scope if interfaces, permissions, environments or baselines change, or if impact is unknown or inputs are contaminated.

Material changes to business rules, architecture constraints or critical assumptions, model assumptions, key acceptance commitments or verification requirements invalidate affected design approval and evidence. Review affected design and tests before changing dependent implementation. A fix within the approved design can retain that design approval with valid evidence bound to the new candidate.

Agree on rounds, runtime limits and resource budget in advance. Estimate startup, checks and model execution from comparable work, labeling and calibrating estimates when data is missing. Failures, timeouts, recoveries and resends accumulate across sessions, candidate changes and commits. Use task-specific limits. Report progress and remaining work when time runs short and obtain approval before continuing. Keep budgets and test timeouts intact. At exhaustion, stop blocked actions and notify the coordinator and requirements owner. Keep review independent and continue unrelated authorized work.

## 3.6.1 Exact candidate and trusted re-verification

Run trusted full checks on the exact final combination under the project contract. Unit results prove their units. Use a clean copy and the required environment, isolated from unrelated worktree changes, global ignores, local configuration and untrusted executables. Git checks require verifiable comparison inputs. A Git-free copy needs an independently verified comparison snapshot bound to the candidate. Missing or unverifiable baselines block approval.

The adopting project maps quick, affected, full, test-diff protection, trusted toolchain, isolation and dependency policies. Missing required mappings or authorization leave dependent checks unrun and stop dependent actions. Use authorized tools without temporary installs, elevation or guard bypasses. Author-local passes and editable success files are author-side evidence only.

Before reuse, verify still-identical input identity, scope, toolchain, commands, environment and export method, and cite the basis. Verify actual evidence against planned checks. Issue a new conclusion for a changed candidate and address new required failures. Rerun affected checks and this round's original failures, expanding for unknown impact. Keep evidence for effectively replayed and closed historical failures under unchanged conditions. Role changes, archiving and closing alone need no repeat check.

In the original record retain conclusions, open issues, unverified scope, executors, commands, exit codes and original evidence links. Reproduce runner summaries using their actual fields. Apply [evidence retention](evidence-retention.md) to originals.

## Actual behavior acceptance

Verify CLI/UI, identity, permissions, external input, concurrency, storage, recovery, installation and runtime integration at actual public entry points. Distinguish real execution from unverified scope across files, databases, processes, browsers, isolated applications and services. Missing environment or authorization means unrun. Explain inapplicability where no corresponding runtime behavior exists.

Keep machine and human test-diff review. Check important states against applicable models and real replays. Verify host isolation, operational authorization and external execution through applicable evidence. Record location, expectation, observation and evidence on failure. Repair under section 3.5 and re-review.
