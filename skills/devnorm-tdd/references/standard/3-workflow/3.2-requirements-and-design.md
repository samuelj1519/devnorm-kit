# 3.2 Requirements and design

Resolve unknown impact through investigation or an authorized minimal experiment. Do not start runtime implementation before scope and impact are bounded.

The coordinator confirms the goal, scope, current version, and acceptance criteria. Define interfaces, state ownership, failure handling, and recovery from unknown results. Record key choices in an [architecture decision](../../../assets/templates/architecture-decision.md) approved by the requirements owner. The [architecture description](../../../assets/templates/architecture.md) identifies code responsibilities, dependencies, and invariants. Agents read only current decisions relevant to the task.

Trace entry points, data flow and existing conventions. When changing a name, entry point, behavior or contract, trace the applicable old names, addresses or behavior to affected callers and similar paths. Check related code, copy, documentation, configuration and tests. Scope the changes and verification. Define core types, reads, writes and state owners before main logic. Give concurrent actors separate write targets where possible. Add synchronization only for state that must be shared.

For observable behavior, compatibility, or performance questions, inspect evidence first. Run a minimal experiment within scope when needed, then choose from its results. Product preferences and key trade-offs belong to the requirements owner. Experiment only to resolve uncertainty that affects the current task. Record inputs, expectations, and observations. A temporary experiment is not a production implementation.

For performance, build or compile volume, dependencies, intermittent failures, and resource use, a plan or task brief must satisfy the measurement requirements of [measure before judging](../1-principles.md#133-root-causes-and-related-defects). A plan without measured data is returned at review.

A product without UI, or a requirement with an existing prototype, needs no additional prototype. Add missing behavior descriptions or obtain clarification from the requirements owner. Create a prototype only to resolve a new UI question without a usable reference. Actual interaction still requires section 3.7 acceptance.

Put new agreements into the current plan. Retain old decisions and approvals as records. Resolve unclear requirements or interfaces here. Check existing authorization for dependencies, software, permissions, real-data access, deletion, installation, and push. Prepare exact objects and changes before requesting missing authorization. If a goal is rejected and will not continue, record abandonment and notify the requirements owner.

## Existing architecture and current constraints

Trace a representative call path against the current architecture and approved decisions. Extend the existing contract and recheck old behavior when the boundary still works. Include the necessary behavior-preserving refactoring when the boundary is sound but the interface or organization prevents the change. When responsibilities, state ownership, dependency boundaries or key assumptions no longer hold, compare viable adjustments and define migration and recovery. Update the current plan and affected decisions. Complete applicable prior review when changing a critical guarantee.

For a new critical boundary or a cross-module redesign, show the changed responsibilities, dependencies, public entries, state writers and transaction boundaries. Compare a real scenario before and after the change. Pick a plausible follow-up rule change and identify the responsibilities and callers it would affect. For each key constraint, record the actual path, what a violation looks like, how to check it and what counts as a pass. Test automatable boundaries with valid and invalid examples. Correct violations of approved boundaries even when functional outputs are correct.

Before dividing work on a shared hot path, key state or a cost-sensitive resource, specify affected callers and business scope, representative load or state, baseline and observable regression criteria. For compatibility, migration or recovery, identify supported consumers and data formats, reads and writes while old and new processes coexist, what a reverted version can read, and when to stop increasing exposure.

## Design and test design review

Record the necessary design and complete review unit for a formal task in the existing task record. A change to critical guarantees, including permissions or trust boundaries, shared writes or transaction ordering, data integrity, migration or recovery, or an irreversible real effect requires non-author review of the design increment, applicable architecture and test design before substantive implementation. Investigate unknown impact first. Once known, apply the applicable review requirements. Review at least state ownership, inputs that can change across async work, fresh validation at final writes, and shared constraints on initial, failure and recovery paths. Review the exact current inputs. Resolve blockers before affected implementation.

When prior review is required, review the design and test design together. Other formal work may use this sequence within the approved project trial when impact is known and bounded, key guarantees remain unchanged, and the reviewer can verify material outcomes through the relevant entry points. Record the rationale and scope in the existing task record.

A non-author reviewer opens a fresh session and records the exact inputs, conclusion, and blockers. Use the same plan to describe the designs involved in the change. For each affected key commitment, specify the expected result, verification method, and required evidence.

| Design area | Acceptance design to agree during review |
| --- | --- |
| Product behavior | User-visible outcomes, allow and reject conditions, and failure and recovery scenarios. Use state models, decision tables, or acceptance cases as applicable. |
| Architecture and module organization | Module responsibilities, dependency direction, state ownership, transactions, and external boundaries. Check existing evidence, models, or necessary minimal experiments to establish that critical assumptions are feasible. Agree applicable architecture checks, integration tests, or real-entry acceptance. |
| Core algorithms and code logic | Input domain, boundaries, expected outputs, and invariants. Use boundary cases, property tests, or unit tests as applicable. State workload, environment, and thresholds for resource or performance commitments. |

Finalize the plan together with the key scenarios for applicable unit, integration, and acceptance tests. Specify the starting state or workload, input or event order, expected outcome and side effects, what to observe, and the environment. Write test code and fill in routine case details during implementation as needed. Handle state risk under section 3.2.1 and map critical transitions and failure sequences to runtime tests. Derive acceptance expectations from agreed specifications, domain rules, trusted examples or approved prior behavior. Keep portable business expectations in independently readable examples. Use the relevant environment for evidence about permissions, concurrency, persistence and external effects. During implementation verification, prove that checks detect the relevant errors for key protections and risks of a false pass.

During prior review, match each key commitment to an assertion or observation. Trace planned entry points, writes, configurations, and external side effects back to the plan and verification scope. Decide how to cover gaps through a test, architecture check, minimal experiment, or targeted manual verification. Resolve blockers before dependent implementation. Use the same reviewer for candidate review under section 3.6 when available.

## 3.2.1 Plan state modeling and review

Before design review, the plan owner assesses state risk and records why modeling applies or does not apply. Use the bundled [state-modeling method](../../methods/statechart/METHOD.md) when:

- A multi-state workflow has complex failure, rollback, or recovery branches.
- Ordering of concurrency, async work, retries, timeouts, or cancellation affects results.
- Transitions affect permissions, idempotency, transactions, or consistency and require invariants.

A structure diagram, interface review, and tests may suffice for module responsibilities, fields, or simple synchronous logic.

1. Define states, events, transition conditions, invariants, termination, and assumptions.
2. Follow the [environment check](../../methods/statechart/METHOD.md#environment-and-limits) for the existing Java and TLC tools, then run the model through the controlled entry. If the host exposes `/statechart`, verify its actual tool against the same requirements. Produce a chart and report. Check safety, deadlock, important state reachability and termination. Record bounds, unchecked properties and chart omissions. Split large charts by responsibility while keeping critical branches and violation paths.
3. The reviewer performs a chart review against requirements, tracing normal, failure, retry, timeout, cancellation, and recovery paths. Check exits, return paths, ownership, and conflicts.
4. Analyze each counterexample. Distinguish modeling errors from design errors, repair the appropriate artifact, rerun, and preserve the original failure and resolution.

Before dispatch at section 3.3, complete all required properties, resolve blockers, obtain the reviewer's chart-review result, and have the requirements owner confirm critical semantics. Preserve corresponding plan, model, configuration, chart, report, and rerun command versions. Stay in this step when tools are missing, required properties are unchecked, or review fails. At the waiting limit, report BLOCKED. Never weaken properties to remove a model counterexample. In the review decision, name the models to rerun and the scenarios to replay through real entry points under section 3.7 after implementation.

The [persist-before-ack example](../../../assets/templates/examples/persist-before-ack.md) shows how to record model findings and implementation replay.
