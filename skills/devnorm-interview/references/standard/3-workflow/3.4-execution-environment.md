# 3.4 Execution environment

For direct execution, verify working directory, version, scope, and existing changes, then proceed to section 3.5. Do not dispatch work to yourself. Use the project's declared execution contract; a maintainer's local configuration does not establish consumer tools or permissions.

## Delegation across terminals

Before entering another assistant's shared terminal, verify working directory, terminal, session ID, and launch batch, then acquire that terminal's input mutual-exclusion lock. Confirm input mode while holding the lock, send one short message, confirm receipt, and release only your own lock. Keep the full task in its brief and send its path. Processes launched by the same coordinator may not input concurrently either. Do not input without a lock, with uncertain identity or mode, or while another operator is present. Stop further input after a release failure. Independent API sessions use the host's verified identity and request-correlation mechanisms, without fabricating a shared terminal or held lock.

An authorized user handles login and workspace trust. Before approval, match the terminal, session, launch batch, and request. Read the full request and change, confirm scope, take one action, then reread state. Do not send task text into an approval menu. GUI permission remains per action as agreed. Do not broaden it to a session or permanent permission.

For unconfirmed receipt or unknown outcome, query the original operation read-only. If you cannot prove it was not sent, do not paste again, append Enter, or resend under a new ID. Proceed to section 3.5 only after confirmed receipt and lock release. At the limit, report the task, request ID, exit code, last state, and lock status to the coordinator. Execution approval still requires the exact request and scope check.

## Project execution contract

The execution contract maps actual project resources, checks, and isolation. It is neither a new platform nor mandatory JSON. Reference existing project rules first, adding missing information to the adoption record rather than maintaining duplicate configuration.

| Project declaration | Minimum content |
| --- | --- |
| Adoption and resources | Approved standard version, accessible standard and method locations, project differences and approval. Package resources must be independently locatable, without sibling skills or maintainer absolute paths. |
| Checks and trusted sources | Actual quick, affected, full, and test-diff protection commands and scope; toolchain, dependency, and baseline origins and how they are distinguished from untrusted author copies. |
| Isolation and data | Clean input copy or worktree, test data and output directories, permission boundaries, and real-service and credential restrictions. Missing isolation or environment is reported as not run. |
| Evidence and resource lifecycle | Accessible existing task records and original logs, access and retention policy; owners of creation, verification, and release of temporary processes, worktrees, locks, and configuration. Active or referenced evidence is not removed as temporary data. |

Example commands are not executable requirements. Execute only explicitly mapped commands whose resources, dependencies, and authorization exist. Identify missing required mappings and stop dependent actions. Do not guess paths, auto-install, elevate permissions, or substitute an empty successful check. The main entry and standalone skills provide the same guarantees.

Package documents distinguish bundled resources, project mappings, and examples. Inline `project:` means map through the project contract first; `example:` means it is not an executable requirement. Shell fences may use `sh project` or `sh example`. These are documentation tags, not command arguments. The `run:` tag and direct bundled entries in ordinary shell fences require regular files with mode `0755`. Interpreter-read scripts and libraries may be `0644`; a shebang alone does not require an execute bit.

Resource checks validate only recognized literal paths, relative TS/JS runtime imports, and direct-entry modes. They do not execute code or establish arbitrary shell behavior, computed imports, dynamic host inputs, or external-package availability. Declare runtime dependencies through provenance and the project contract. Missing or untested requirements remain pending; static success is not actual client acceptance.

## 3.4.1 Agent permission provisioning

Before dispatch, choose least privilege by task responsibility and actual host capability. Independent reviewers write authorized reports by default, not implementation or permission changes. Implementation permission does not automatically cover commits, pushes, dependency changes, installation, or public release. Apply existing authorization within its original scope without asking again or expanding it. Before long-running or paid calls, use a minimal non-model preflight to check required read/write locations, isolation, identity entry, and commands; do not repeat it for unchanged conditions. When the host permits, group known related actions within the same authorization boundary while retaining each outcome. A batch must not broaden paths, permissions, or effects, or bypass host per-action approval. Query unknown outcomes rather than resending to reduce waiting.

The project declares boundaries for network fetching, remote access, elevation, Git history and remote rewrites, dependency changes, execution bypassing lockfiles, publication, and credential access. Do not evade restrictions through wrappers, prefix escapes, other authentication, or other remotes. Compound-command safety depends on the host's actual parsing and checks. Prefix-based adapters must account for segmentation and wrapper escapes, rather than presenting one CLI's rules as universal isolation.

Deny lists intercept only some spellings and cannot alone prove irreversible operations are blocked. When required, combine authorized, verifiable credential isolation, operation-entry restrictions, and post-action guards, stating each layer's limits. Detection afterward is not prevention. Branded source-maintenance CLIs, cache directories, SSH managers, and guard scripts belong to the maintenance layer; consumers need not possess or execute them.

For temporary provisioning, record previous values, ownership, and restoration conditions, without overwriting existing local configuration. At completion verify and release this task's resources, not other owners' configuration or evidence under investigation. Query unknown outcomes first; preserve state and report restoration failures. The project explicitly declares check exclusions, limited to actual runtime directories rather than same-named files or broad exclusions that hide input changes.

## Chinese writing responsibilities

The project assigns authors or final editors by actual language capability, without mandating a model or another agent. Honor existing explicit writing responsibilities. If a designated executor is unavailable, retain failures and undelivered status and use authorized fallback arrangements; do not fabricate an author or reviewer.

Human-facing rules, reports, commit messages, and handoffs use accurate, restrained Chinese: lead with conclusions and scope, keep one main point per paragraph, and retain facts, conditions, risks, and unverified scope. Preserve technical terms, paths, commands, and machine fields. Do not invent test totals or make claims more certain through wording. Reference actual project-specific writing resources when provided. Missing specialist references do not waive these basic requirements. Writing quality checks and nonauthor review are distinct responsibilities, not substitutes.
