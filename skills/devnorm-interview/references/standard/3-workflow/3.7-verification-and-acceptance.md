# 3.7 Verification and acceptance

Complete outstanding applicable checks. For UI, apply the [UI checklist](../5-ui-acceptance.md), including first use, empty/error/loading states, narrow width, dark mode, keyboard, accessibility, AI output, layout, and side-by-side screenshots. Reuse an existing prototype as the reference.

Record static checks, simulations, browsers, real services, native apps, installed artifacts, and real models separately. Do not start if data directories, processes, windows, and packages cannot be shown isolated from real work. Before model calls, verify authorization, counts, and input/output limits. Separate directories do not isolate billing.

Where section 3.2.1 applies, verify correspondence between plan, model, and implementation, rerun relevant models, convert important counterexamples to executable tests, and replay through actual public entries. Design-only counterexamples repair plans. A claimed implementation defect needs runtime evidence.

Changes to state contracts, critical rules, or model assumptions return to section 3.2.1 for re-review, followed by affected implementation and verification. Update mappings and tests when code changes model correspondence. The requirements owner confirms critical semantics. State model scope and assumptions. Verify actual apps, persistence, and platform behavior separately.

Explain inapplicable checks. Mark missing required environments or authorization unrun. At the limit, notify the coordinator and stop. Product failures return to section 3.5. Unsettled requirements return to section 3.2. Changed inputs require self-check and independent review again.
