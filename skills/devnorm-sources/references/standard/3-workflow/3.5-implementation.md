# 3.5 Implementation and self-check

Edit authorized files only. Preserve originals. Test with fictional samples or temporary read-only copies. Follow the [check schedule](../1-principles.md#15-automated-check-schedule). Verify exact staged and tested versions under [section 6.3](../6-version-control/6.3-staging-and-commits.md#63-staging-and-commits). Mark missing tools unrun. Get approval before installing or copying dependencies.

Verify public entry point results, storage changes, call counts and interaction. Await explicit async completion. Reproduce defects first. Prove critical checks reject runnable faulty or unprotected versions. When existing names, entry points, behavior or contracts change, trace prior use and criteria. Sync authorized updates and explain retained compatibility or historical references.

<!-- devnorm:condition:test-protection:start -->
Authors must not remove or weaken existing tests, or change old assertions to pass a check. If the specification requires a test change, stop and have the requirements owner assign a separate test or tooling task. Explain every test change for section 3.6 review. Reducing check settings or limits requires explicit requirements-owner approval. Run the project's test-diff guard and human review. Missing required protection stops dependent work. Projects select their own tools.
<!-- devnorm:condition:test-protection:end -->

Diagnose runner or environment failures first. Preserve first failure and reruns. Stop affected work and notify the coordinator if tools are missing, isolation unclear or budget spent. Resolve executor, version or scope conflicts under 3.3. For 3.6 record the unit, exact version, inputs, logs and unverified scope. Review shared invariants together. Verify the final combination separately.

Repairs, batch failures, executor changes, premise checks, replanning and rollback share one budget. Record negative probes separately. Stop at the agreed limit.

## 3.5.1 Task-specific methods

Record applicable methods in the existing plan, brief or logs. Simple tasks follow section 3.1. See the pinned [poteto-mode playbooks](https://github.com/cursor/plugins/tree/24621dbcc59e205a7faadb0e06d540f91712b5cc/pstack/skills/poteto-mode/playbooks).

| Task | Method and completion evidence |
| --- | --- |
| Defect | Reproduce, diagnose and verify under [defect diagnosis](../../methods/debugging/METHOD.md). After repeated failures test the shared premise under section 1.3.3. Check affected and similar behavior. |
| Refactoring | Fix inputs, outputs, errors and side effects. Check batches against behavior tests. Return required behavior changes to section 3.2 and protect tests. |
| Batch edit | Complete a representative sample. Choose manual work or a rerunnable script by risk and total cost. Check previews and valid and invalid samples, then each batch. Query unknown writes. Confirm coverage, scope and safe repeats. A one-off may be direct. |
| Performance | Follow [measurement](../../methods/benchmark/METHOD.md) for correct output, real workloads, matching environments and the bottleneck. Test one hypothesis per iteration and alternate measurements when needed. Revert only this iteration on regression or no benefit. Keep measurements. |

After the implementation passes applicable checks, a bounded code simplification pass may run before freezing the candidate if it can clearly reduce reading or maintenance cost. Address complexity only within the authorized scope of the task. Keep the changes when they reduce complexity and the affected behavior checks and original-failure replays pass. Return necessary behavior changes to section 3.2.

Set experiment and script authorization, isolation, budgets and stop conditions per task. Confirm ownership and preserve other work before rollback. Recheck versions, inputs and evidence afterward. If the goal remains unmet, continue within budget, replan or report the blocker.

## 3.5.2 Conditional test-driven development

Set observable acceptance and verification before implementation. Prefer [short TDD cycles](../../methods/tdd/METHOD.md) for clear rules, calculations, parsing, state decisions or cheap, reproducible defects. Use TDD when requested.
