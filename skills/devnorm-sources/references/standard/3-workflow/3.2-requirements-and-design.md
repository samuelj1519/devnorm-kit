# 3.2 Requirements and design

Resolve unknown impact through investigation or an authorized minimal experiment. Do not start runtime implementation before scope and impact are bounded.

The coordinator confirms the goal, scope, current version, and acceptance criteria. Define interfaces, state ownership, failure handling, and recovery from unknown results. Record key choices in an [architecture decision](../../../assets/templates/architecture-decision.md) approved by the requirements owner. The [architecture description](../../../assets/templates/architecture.md) identifies code responsibilities, dependencies, and invariants. Agents read only current decisions relevant to the task.

Trace entry points, data flow, and existing conventions. Define core types, reads, writes, and state owners before main logic. Give concurrent actors separate write targets where possible. Add synchronization only for state that must be shared.

For observable behavior, compatibility, or performance questions, inspect evidence first. Run a minimal experiment within scope when needed, then choose from its results. Product preferences and key trade-offs belong to the requirements owner. Experiment only to resolve uncertainty that affects the current task. Record inputs, expectations, and observations. A temporary experiment is not a production implementation.

A product without UI, or a requirement with an existing prototype, needs no additional prototype. Add missing behavior descriptions or obtain clarification from the requirements owner. Create a prototype only to resolve a new UI question without a usable reference. Actual interaction still requires section 3.7 acceptance.

Put new agreements into the current plan. Retain old decisions and approvals as records. Resolve unclear requirements or interfaces here. Check existing authorization for dependencies, software, permissions, real-data access, deletion, installation, and push. Prepare exact objects and changes before requesting missing authorization. If a goal is rejected and will not continue, record abandonment and notify the requirements owner.

Before substantial implementation, high-risk tasks changing critical guarantees or with unknown impact need review of this increment's plan and architecture. Ordinary tasks establish necessary design without automatic prior independent review merely for input or storage work. Section 3.2.1 still determines model applicability. Record exact inputs, reviewer, conclusion, and unresolved issues in the task brief. Do not proceed after a failed review. An earlier project review does not cover a new change, and completed implementation cannot retroactively establish prior approval. Check data ownership, inputs that can change across async work, fresh validation at final writes, and consistent initial/failure/recovery behavior. Simple low-risk work still follows section 3.1.

## 3.2.1 Plan state modeling and review

Before design review, the plan owner assesses state risk and records why modeling applies or does not apply. Use `/statechart` when:

- A multi-state workflow has complex failure, rollback, or recovery branches.
- Ordering of concurrency, async work, retries, timeouts, or cancellation affects results.
- Transitions affect permissions, idempotency, transactions, or consistency and require invariants.

A structure diagram, interface review, and tests may suffice for module responsibilities, fields, or simple synchronous logic.

1. Define states, events, transition conditions, invariants, termination, and assumptions.
2. Write the model with `/statechart`, run TLC, and generate a chart and report. Check safety, deadlock, important state reachability, and termination. Record bounds, unchecked properties, and chart omissions. Split large charts by responsibility while keeping critical branches and violation paths.
3. The reviewer performs a chart review against requirements, tracing normal, failure, retry, timeout, cancellation, and recovery paths. Check exits, return paths, ownership, and conflicts.
4. Analyze each counterexample. Distinguish modeling errors from design errors, repair the appropriate artifact, rerun, and preserve the original failure and resolution.

Before dispatch at section 3.3, complete all required properties, resolve blockers, obtain the reviewer's chart-review result, and have the requirements owner confirm critical semantics. Preserve corresponding plan, model, configuration, chart, report, and rerun command versions. Stay in this step when tools are missing, required properties are unchecked, or review fails. At the waiting limit, report BLOCKED. Never weaken properties to remove a model counterexample.
