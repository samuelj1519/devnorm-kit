# Task planning

Use for multi-step work or before delegation. Reuse the task brief. Do not force small low-risk tasks into separate work items.

1. Split around demonstrable or independently verifiable outcomes. State inputs, outputs, completion evidence, and true blocking prerequisites. Reading order is not a dependency.
2. Follow actual interfaces and state ownership. Keep small tasks, coupled design, and expensive-to-receive work with one executor. Batch migrations into verifiable units. Do not force every item through database/API/UI or add temporary compatibility by default.
3. Preserve exact versions, allowed files, interface owners, single writers, execution/review owners, checks, cumulative budget, and return conditions in the [short brief](../../../assets/templates/task-short.md) for formal tasks. Expand applicable sections of the [full brief](../../../assets/templates/task.md) when more detail is needed.
4. Compare briefing, execution, receiving, integration, review, and rework before choosing delegation, models, or concurrency. This method does not authorize starting other agents.
5. Assign one writer to shared interfaces and lockfiles. Complete real prerequisites first and verify each outcome before dependents. Separate passes do not replace checks of the combined result.

Deliver an executable arrangement in the existing record. Return unclear responsibility or acceptance to design. Stop and return under agreed conditions for repeated failed repairs, out-of-scope files, or ambiguous requirements. External tickets, labels, and dispatch retain their actual authorization.

Source: adapted from pinned Matt Pocock to-tickets. Keeps verifiable slices and blocking relationships; incorporates DevNorm ownership, budget, return, and merge conditions.
