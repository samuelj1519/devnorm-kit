# 5.4 Input and confirmation

Prefer reliable defaults, prior input, and current context; common tasks use a short form or a direct action; when there are branches, dependencies, or heavy input, step by what the user must decide now. Fields must explain nearby what is needed; correctable errors must point to the location and the fix; multiple errors should offer a jumpable summary and keep the entered content.

Low-risk reversible actions should take effect promptly with undo. High-impact or irreversible actions must show the object, scope, and main consequences before submission; label the submit button clearly and allow going back to correct. Avoid repeated confirmation for the same plan; reconfirm when the scope, target, or key conditions change; after submission, state what cancel, undo, and recovery can each achieve.

Request permissions and sensitive data at the step where they are needed, showing purpose and scope; offer workable partial-grant, refusal, or later paths; credentials and their outbound destinations must be controlled; important permission changes are viewable and revocable in settings.
