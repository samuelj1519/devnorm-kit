# 5.8 UI acceptance

For UI tasks, record applicability, requirements, results, and evidence for items 5.8.1 through 5.8.11 in the [task brief](../../../assets/templates/task.md). Use `N/A` with a reason for inapplicable items and `not_run` for missing execution. Repair failures and rerun. Script success does not replace actual interaction acceptance; applicable required failures prevent completing the task. State when a task has no UI.

| ID | Required checks |
| --- | --- |
| 5.8.1 | First use: explain the product within seconds, explain permissions and allow deferral, provide one primary action, and show no fabricated reviews or data. |
| 5.8.2 | Empty state: explain why it is empty and the next action. Reserve accent color for that action. |
| 5.8.3 | Errors: explain the failure, effect, and recovery without blaming the user. Text contrast is at least 4.5:1 and icon contrast at least 3:1. |
| 5.8.4 | Loading: show progress and continued feedback after about 1 second. Allow cancellation for long work. Use honest step descriptions for AI work rather than unexplained endless activity. |
| 5.8.5 | Narrow windows: define the minimum usable width, allow sidebar collapse, prevent reading-area overflow, and use targets at least 24×24 px. |
| 5.8.6 | Dark mode: use semantic color variables rather than light-only hex values, measure contrast, and use opaque backgrounds when Reduce Transparency is enabled. |
| 5.8.7 | Keyboard and focus: align Tab and visual order, keep focus visible, close overlays with Esc, and document common shortcuts. |
| 5.8.8 | Accessibility: meet WCAG AA contrast, use more than color for important actions, test reduced motion, and provide accessible names with assistive technology. |
| 5.8.9 | AI output: label generated content, expose capabilities and limits, and support at least two of edit/regenerate/discard. Verify preview and confirmation for data changes or sends. For an already authorized, low-risk action that can be fully undone, verify undo as an option. Verify prior authorization for high-impact, irreversible or out-of-scope actions under [Input and confirmation](5.4-input-and-confirmation.md). Avoid fabricated accuracy percentages. Provide a non-AI path for high-risk work. |
| 5.8.10 | Layout: group every element, avoid isolated floating controls, and provide one primary action per screen. |
| 5.8.11 | Prototype and implementation screenshots: use the same fictional state and actual container width, preserve side-by-side evidence, and state acceptance boundaries per task. |

Specify project requirements and evidence for each applicable item. Collect evidence along affected user paths. In the same task record, map verified items, required checks not run and reasons for inapplicability to the individual checklist items. Use this checklist and its defaults where project UI guidance is absent or incomplete. Keep stricter project requirements. See [Accessibility and device support](5.6-accessibility.md) for web target sizes, contrast and applicable exceptions, and for native platforms and assistive technology.

Before deleting, reducing, or replacing a requirement, record its ID, old and new requirements, scope, reason, risk, replacement verification, recovery, and requirements-owner approval. Keep the original until approved. No UI or an existing prototype means no additional prototype is needed. Compare screenshots only when a prototype applies, and explain inapplicable items.

At design review, write a short task card for each frequent path: user and situation, completion criteria, starting point, required choices, defaults, exceptions, test devices, and evidence. Task instructions describe the goal only, without operation answers. First observe real users completing the task unaided from the card, recording whether they finish and where they pause or need help, then retest changes under the same conditions. When comparing designs, use repeatable tasks with observable success criteria and record completion, time, abandonment, and perceived success; record samples, tasks, environment, and comparison scope together.

| Acceptance item | Observe at least |
| --- | --- |
| First use and daily reuse | Whether finding entries, selecting objects, completing tasks, and confirming results need outside help; record repeated input, misselections, and backtracking |
| Search, cross-device, and assisted input | Whether filters, current location, back navigation, drafts, and focus persist; cover the keyboards, touch, and assistive technology the project adopts |
| Boundaries and recovery | Run applicable scenarios such as empty results, errors, denied permissions, offline, timeout, partial completion, and duplicate submission; check the real resulting state and recovery paths. Where relevant, verify complete undo for drafts and reconfirm under section 5.4 when the recipient or scope of a send changes |
| Interface quality | Check typography, semantics, contrast, feedback, and primary actions under narrow windows, long content, enlarged type, and key states |
| Performance | Record time from entry to operable and to actual completion for common tasks; observe whether interaction continues during load, lag, and layout shift; compare the same tasks before and after optimization and state devices and samples |
| Compatibility | For existing products, verify migration of old entries, deep links, automation, and status output; distinguish usability observations from real runtime evidence |

After launch, observe completion rate, errors and recovery paths, time spent, and support feedback; metrics depend on tasks and user groups, so set targets against this project's baseline. Web projects may add loading, responsiveness, and visual-stability data from real visits.
