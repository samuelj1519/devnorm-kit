# 3.3 Task brief and work allocation

Use the [minimum formal task record](../../../assets/templates/task-short.md) for formal work and [full sections](../../../assets/templates/task.md) as needed. Simple work needs no form. Record goals, risks, scope, exact inputs, checks, authorization and stop conditions using the project contract. Check directory, branch and existing changes. Assign one writer per shared interface, lockfile and generated output. Separate source, test data and runtime output.

## One authoritative record

Keep facts, progress, open issues, attributed conclusions and original evidence in the project’s durable, accessible record. Add material changes only. Confirm access to the exact version before dispatch. Handoff repositories are optional. Set verifiable outcomes. Cite the uncovered requirement, change or risk for extra reading, reruns or reports.

For each key commitment, link its expectation, required evidence, owner and original logs in the same record. Refer to applicable architecture decisions, models, delegation or release records. Keep approvals and conclusions with their respective records.

Identify subtasks, commits, review units and the final combination separately. Units cover independently assessable behavior, tests and documents. Review shared invariants together. Final combination checks remain due.

## Execution and review allocation

Set whole-task acceptance scenarios and shared constraints. Resolve uncertainty about feasibility before dividing work by observable behavior. Connect one representative end-to-end path as an early check. Independent parts can proceed in parallel once shared contracts, input dependencies, writers and return evidence are clear. Verify that the parts meet joint commitments on normal, failure and recovery paths.

Estimate work, dependencies and parallelism. Include briefing, execution, context recovery, integration, review and rework when comparing direct work with delegation. Label estimates and unknowns. Keep work with its executor when handoff needs extensive reinterpretation. Small tasks, coupled changes and overall design usually have one executor. Formal work has one qualified non-author primary reviewer.

Before delegating, check capabilities, tools, quota and project limits and agree on [return conditions](../../../assets/templates/task.md#return-conditions-for-delegated-work). Stop affected work and preserve state at unauthorized changes, critical ambiguity, repeated failures or budget exhaustion. The coordinator chooses whether to revise the design, implementation, environment or allocation. Continue unaffected authorized work. Query unknown outcomes before retry. Accumulate waiting, rework, review, timeouts, recoveries and resends within the agreed budget. Agree on missing limits without copying model examples. Exhaustion stops dependent work and leaves independent review due.

Choose arrangements from the actual change under section 3.1. Formal work follows applicable [design and test design review](3.2-requirements-and-design.md#design-and-test-design-review) and section 3.2.1 modeling, with exact inputs and conclusions in the task record. Complete required behavior checks, independent review and applicable acceptance. After repairs follow [section 3.6](3.6-independent-review.md). For integration targets verify the exact final combination under [integration](integration.md).

Reuse evidence only for identical inputs. Verify origins, source, rules, dependencies, samples, tools and environment. Link original logs and identify reuse. Trial new arrangements with agreed scope, stop conditions and comparable quality and total-cost measures. Use existing approvals for safeguard reductions.
