# 3.1 Task classification

<!-- devnorm:route:start -->
<!-- devnorm:condition:simple-route:start -->
Use two task types: simple and formal. Handle a simple task directly when the goal, scope and authorization are clear, the impact is known, bounded and recoverable, the existing contract and critical guarantees stay intact, and an effective check can be performed independently. Text edits and bounded logic or settings repairs within an existing contract can qualify. Classify by actual impact, using the technology and file scope to investigate affected behavior.

Use the formal route for tasks that do not qualify as simple. Only formal tasks follow the standard workflow. Derive the necessary design, prior review, models, checks and actual acceptance from the change. One non-author primary reviewer checks the exact candidate.

Finish a simple task after necessary checks and a brief result with unverified limits. Skip the full workflow, capability index and task brief. If simple-task conditions cease to hold, stop affected writes, switch to the formal workflow and invalidate affected evidence. Investigate unknown impact and stop actions lacking necessary authorization. Stricter project rules and trusted full checks before integration still apply.
Regressions or repeated failure require the standard workflow and inclusion in quality statistics.
<!-- devnorm:condition:simple-route:end -->
<!-- devnorm:route:end -->

Do not weaken assertions, disable checks or ignore unknown impact to qualify for direct handling. Adding an effective regression assertion does not automatically change task classification. Give a reason for every test change and follow the current review requirements. Obtain applicable approval before reducing safeguards. [Implementation and self-check](3.5-implementation.md)

Persistence and external input are investigation cues. Classify work by what changes in the contract and critical guarantees. Read the relevant plan or module record when you need to establish impact.

For example, when repairing a documentation anchor, search for the old anchor and known callers, then check which case applies.

- References are confined to the repository. The impact is bounded and recoverable. Fix the anchor or references as a simple task and run the applicable link check.
- Published material or a compatibility entry could reference the old anchor, so the impact remains unknown. Pause affected writes. If investigation confirms a change to promised access behavior, handle the task as formal work. If the task still satisfies the simple criteria, handle it directly.
