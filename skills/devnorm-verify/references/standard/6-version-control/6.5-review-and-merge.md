# 6.5 Review and merge

Complete applicable review, acceptance, and trusted full checks under [sections 3.6 through 3.8](../3-workflow/3.6-independent-review.md#36-independent-review). Confirm the exact candidate, target branch, and combined contents. Recheck affected conclusions after conflicts, base updates, or candidate changes. Do not move the target branch before checking the combination.

GitHub required checks must correspond to the current candidate and required combination. Confirm that applicable checks actually ran. A `skipped` or `neutral` result, or a job skipped after a dependency failure, does not establish compliance by itself. Required combination versions, including operating systems, must actually be run. Do not drop a combination because a problem appears only on that combination. Bind trusted check sources where supported. Local hooks and author-editable success records do not replace trusted merge conditions.

Record independent agent review and GitHub account approval separately. A PR author cannot approve their own PR; multiple sessions using one account do not constitute another account's approval. Configure requirements for the actual accounts, plan, and check services. Do not claim unavailable approvals passed.

Merge with the selected merge, squash, or rebase method, consistent with section 6.1 and the scope of this approval. Retain necessary authorship and task links. Verify the resulting commit and target state. Normally finish the original task branch after a squash and begin later work from the updated main branch. If a busy project uses a merge queue, separately verify combination checks and required CI triggers such as `merge_group`; queues are not a default requirement for all projects.
