# Integration

<!-- devnorm:condition:integration-trusted-full:start -->
Before updating a project-designated integration target, verify authorization, exact candidate, target branch, inputs, and check configuration. This includes merge, integration cherry-pick/rebase/squash, and direct commits or pushes to that target. Ordinary task-branch commits use quick checks, not automatic full checks. A trusted check service or merge tool confirms full checks on the exact combination, including all applicable tests, dependency checks, security scans and no coverage decline. Execute the full command registered in the project contract. Author-edited success records and local quick checks are insufficient. Missing tools or unclear evidence stop merge.
<!-- devnorm:condition:integration-trusted-full:end -->

Reusing an item of evidence requires proof that the source, rules, dependencies, samples, environment, security data, and coverage baseline it covers remain identical; old candidate approval does not transfer to a new candidate. Before consolidated checks, prepare the combined version only in an isolated directory or temporary index. Do not move the target branch or create a real merge commit. Merge after these checks and applicable acceptance pass. Changes, conflicts, or contamination return to section 3.5 and review of affected scope under section 3.6; expand scope for unknown effects. Semantic-unit success is not combination success. Direct tasks not updating an integration target need not run this step.

For example, a reviewer starting from commit A examines the task diff, while a local commit check compares the staged tree with the version tested. If the target moves from A to B, combine B with the task changes in isolation and run trusted full checks on that new combination before updating the target. The earlier diff and staged record can still serve their own purposes. The previous combination’s checks cannot approve the new one.

Commit only approved files with normal hooks and protect others' work. Correct shared history with new commits by default. Apply [section 6.6](../6-version-control/6.6-undo-and-history.md#66-undoing-changes-and-editing-history) to unshared editing, approved history replacement, and tags; ordinary commit or push authorization grants no exception. Check PRs, check statuses, and merge methods under [sections 6.4 and 6.5](../6-version-control/6.4-pushes-and-pull-requests.md#64-pushes-and-pull-requests). Installation, release, and push retain their own authorization. If merge succeeds but cleanup fails, report merged with completion blocked and notify the coordinator rather than claiming full completion. Record author-side checks passing, handover to independent re-verification, and overall completion separately. Planning a handover is not completion and does not by itself record `BLOCKED`.
