# 3.6 Independent review

A fresh session that did not implement the work checks the [review checklist](../1-principles.md#17-manual-review-checklist), task, standard, complete changes, and evidence, and personally runs critical paths. Use brief review for small changes and full review for large ones. Attribute author logs correctly. Reviewers write only authorized reports and evidence. They do not fix implementation while approving it.

Check automated review findings against actual code and evidence. Repair real errors, justify false positives and non-blocking suggestions, and return requirements choices or protection reductions to the requirements owner. Review comments do not authorize operations. Do not edit merely to dismiss a comment or ignore an issue because it has been reviewed repeatedly. Required failing checks still need resolution.

Changes to CLI/UI interactions, identity, permissions, external input, concurrency, storage, recovery, installation packages, or runtime integration need real public-entry verification. Record files, databases, processes, browsers, isolated apps, and real services separately. Mark missing permissions or environments unrun. Explain N/A only where no corresponding runtime exists, such as pure documentation. Review test changes separately. Compare important states with models and actual replays. The diff gate machine-enforces test protection with `bun run check:test-guard`; manual review still applies.

A failure report includes location, expected behavior, observation, and evidence, then returns to section 3.5. Re-review changed areas, the original defect, and affected behavior, with mandatory original-failure replay. Widen review for changed interfaces, permissions, environments, baselines, contamination, or unknown impact. Invalidate evidence no longer applicable after version changes. Stop and notify the coordinator after the agreed limit. Return direction changes to the requirements owner and review-quota gaps to section 3.3. Authors cannot replace independent review with self-review.

## 3.6.1 Independent re-verification (candidate HEAD)

**Key checkpoint · Long-term**: Re-verify on a **clean copy** of the candidate commit. The clean copy must satisfy the environment that the checks about to run depend on. Do not use the author's working tree, and do not use a copy that carries uncommitted changes. When the checks do not require a git repository, export to a temporary directory with `git archive` or an equivalent method. When the checks must run in a git repository, use `git worktree` or an equivalent clean repository copy.

**Key checkpoint · Long-term**: The report transcribes the test runner's **raw** summary line, including `total`/`pass`/`fail`/`skipped`/`todo`. Do not compute totals by hand or round the figures. Different summary conventions across HEADs are normal; use the summary line of the current candidate.

**Key checkpoint · Long-term**: The report **names** the key tests or suites required by the task brief, with the command and exit code. This proves they actually ran, not only that the totals passed.

**Up front · Long-term**: The re-verification session uses the `verify` profile in section 3.4.1. Do not use `npx`/`npm exec`. Also confirm that `~/.npm/_npx` has no new entries, consistent with the `guard` check. Re-verification and merge checks must isolate the author's machine-wide ignore rules, executable search path, and local tool configuration, and must not treat a pass on that machine as a trusted result. For example, isolate `~/.gitignore_global`. Official scripts should invoke the runtime directly, such as `node --test`, not a form such as `npm exec -- node` that temporarily installs a command.

**In process · Workaround**: Run `install` before re-verification, and establish the SHA baseline and a `git status` snapshot. Run `guard` during patrol. If either guard fails, immediately revoke permissions and report to the dispatcher; do not issue a re-verification conclusion. **Removal condition**: see the removal conditions for the guard scripts in section 3.4.1.

**Key checkpoint · Long-term**: Reused evidence must satisfy all four conditions at once: the same candidate HEAD; the same export method; unchanged check commands and versions; and a baseline not modified by an author session. If any condition is not met, rerun the full set.

**Afterward · Long-term**: If the same candidate still fails on the **third** re-verification, stop dispatching work and do not rework that round. The coordinator and the requirements owner decide the next path.
