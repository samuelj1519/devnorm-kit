# 3.5 Implementation and self-check

Edit only authorized files. Use fictional samples or temporary read-only copies and preserve originals. Follow the [automated check schedule](../1-principles.md#15-automated-check-schedule) for pre-write permissions, post-edit formatting and code checks, and pre-commit quick checks. Commit only with authorization; check exact staged content and the actual tested version under [section 6.3](../6-version-control/6.3-staging-and-commits.md#63-staging-and-commits). Mark missing tools unrun. Do not install or copy dependencies without authorization.

Verify actual results, storage, call counts, and interaction state through public entry points. Wait for explicit async completion. Reproduce defects before repair. For critical protection, run the old incorrect logic or a version with protection removed and prove that the check detects the error.

Authors must not remove or weaken existing tests or change old assertions to pass checks. If the specification requires a change, stop and have the requirements owner assign a separate test/tooling task. Explain all test changes for section 3.6 review. Tighten check configuration and limits by default. A reduction requires explicit requirements-owner approval. The diff gate registered in the project contract machine-enforces test protection; manual review still applies. Missing required protection stops dependent actions without requiring the target project to adopt Bun or this repository's scripts.

Repair product errors here. Diagnose test-runner or environment failures first, preserve the initial failure, and do not select one successful run for reporting. Stop and notify the coordinator for missing tools, uncertain isolation, or exhausted budget. Return to section 3.3 for quota replacement, version conflict, or scope conflict. After self-check, fix the complete semantic review unit, exact version, inputs, logs, and unverified scope in the original record and proceed to section 3.6. Local commits and implementation subtasks do not each require a separate review. Review related invariants together and verify the final combination separately.

Self-repair and repairs after batch failure consume the same cumulative task budget. A new executor, premise test, replan, or rollback does not reset it. Separate expected negative probes from actual rework. Stop at the agreed limit even when a premise still needs investigation.

## 3.5.1 Task-specific methods

These methods draw on the pinned [poteto-mode playbooks](https://github.com/cursor/plugins/tree/24621dbcc59e205a7faadb0e06d540f91712b5cc/pstack/skills/poteto-mode/playbooks). Select what the current problem needs and record it in an existing plan, task, or log. Do not run every method or create duplicate records. Simple low-risk tasks still follow section 3.1.

| Task | Method | Completion evidence |
| --- | --- | --- |
| Bug fix | Reproduce in the relevant runtime, state testable causes, and narrow them with minimal input, logs, or controls. After repeated failure, test the shared premise under section 1.3.3. | Original reproduction passes, the runnable incorrect version is detected, and affected behavior and related paths are checked. |
| Behavior-preserving refactor | Freeze representative inputs, outputs, errors, and side effects before structural edits. Add or reuse behavior tests. Change in checked batches without feature changes. | Contracted behavior remains. Return required behavior changes to section 3.2 and protect tests. |
| Batch edit | Complete a representative sample. Choose manual work or a rerunnable script by risk and total cost. Check preview, valid and invalid samples, then run checked batches. Query written state before retrying an unknown outcome. | Complete in-scope changes follow the sample rule without extra writes. Repetition does not duplicate edits. A small one-off does not require a tool. |
| Performance change | Freeze correct output, real workload, and environment. Obtain bottleneck and baseline data per [measure before judging](../1-principles.md#133-root-causes-and-related-defects). Test one hypothesis per iteration, compare actual work and results, and alternate repeat measurements where needed to identify noise. | Correctness and error counts hold and the performance target is met. Remove only this iteration's changes after no benefit or regression, preserving measurements. |

Experiments and scripts retain authorization, data isolation, and budgets. Set measurement counts and stop conditions per task. Ordinary edits do not require performance testing. Report BLOCKED at the budget limit.

Before rollback, confirm ownership and preserve others' and pre-existing changes. Recheck versions and inputs afterward. Evidence reuse still follows sections 3.3 and 3.6. Removing an unhelpful change does not fulfill the original goal. Continue within remaining budget, return for replanning, or report blocked.

## 3.5.2 Conditional test-driven development

Before implementation, establish observable acceptance and verification. Prefer small TDD cycles for clear business rules, calculations, parsing, state decisions, or cheaply reproducible defects; follow an explicit user TDD request. Add one expectation, observe failure caused by missing behavior, implement the minimum, and make necessary structural improvements while green before the next behavior. Do not write every unit test up front.

Choose the test level for the behavior: unit tests for pure logic and appropriate integration/contract tests for storage, protocols, and service boundaries. Concurrency and recovery retain applicable modeling and real acceptance. Verify UI exploration, prototypes, copy, and simple configuration by risk. Investigate or experiment when behavior or a low-cost test path is unclear, and explain substitute verification.

Compilation, import, environment, and probe errors are not valid failure evidence. Derive expectations from requirements or independent examples rather than copying the implementation algorithm. Preserve existing tests, assertions, and checks under sections 3.5 and 3.6. TDD does not replace independent review, target-host acceptance, or full merge checks.
