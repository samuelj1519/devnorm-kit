# 3.7 Verification and acceptance

Run outstanding applicable checks on the exact candidate. Use the key commitments, expected results, and verification methods agreed in the design. Cite actual results in the existing task record. Use code coverage to identify paths that did not execute. Each key commitment needs evidence from its corresponding assertion or observation. For UI, apply the [UI checklist](../5-interaction-and-interface/5.8-ui-acceptance.md), including first use, empty/error/loading states, narrow width, dark mode, keyboard, accessibility, AI output, layout, and side-by-side screenshots. Reuse an existing prototype as the reference.

Record static checks, simulations, browsers, real services, native apps, installed artifacts, and real models separately. Do not start if data directories, processes, windows, and packages cannot be shown isolated from real work. Before model calls, verify authorization, counts, and input/output limits. Separate directories do not isolate billing.

Where section 3.2.1 applies, verify correspondence between plan, model, and implementation, rerun relevant models, convert important counterexamples to executable tests, and replay through actual public entries. Design-only counterexamples repair plans. A claimed implementation defect needs runtime evidence.

Changes to state contracts, critical rules, or model assumptions return to section 3.2.1 for re-review, followed by affected implementation and verification. Update mappings and tests when code changes model correspondence. The requirements owner confirms critical semantics. State model scope and assumptions. Verify actual apps, persistence, and platform behavior separately.

Explain inapplicable checks. Mark missing required environments or authorization unrun. At the limit, notify the coordinator and stop. Product failures return to section 3.5. Unsettled requirements return to section 3.2. Changed inputs require self-check and review of changes and effects by the original independent primary reviewer under section 3.6. Replace that reviewer when independence or context is no longer trustworthy.

Incremental review scope and cumulative budgets follow section 3.6; exact candidates, clean copies, and guards follow section 3.6.1. Use the task's predetermined stop conditions, not a universal failure count. An unrun mark does not cancel a guard failure; the final combination still requires trusted full checks.

## Verification and recovery after production deployment

<!-- devnorm:condition:production-recovery:start -->
Projects that continuously deploy to production include release verification and recovery in their existing release procedures. Before deployment, verify the exact release artifact and authorization. Record the release owner, initial exposure, observation window, signals, thresholds, stop conditions, and rehearsed containment or recovery steps. Choose signals that can detect relevant user or business regressions. Use progressive rollout where available, or record the approved alternative containment. Set the values for the actual service and risk.

Observe the running release at the real entry points and record actual exposure and results. Stop expanding exposure when a stop condition is met, evidence is insufficient, or the release outcome is unknown. Preserve evidence and determine the actual state from trustworthy read-only evidence. Use authorized recovery, such as rollback, disabling the affected feature, or a forward fix, only when safe for data and external effects. Otherwise keep the rollout paused and escalate to the owner. Verify actual behavior and all applicable affected data and external side effects. Confirm that any irreversible effects were handled as specified and check that the observed signals have recovered. If recovery verification fails, evidence is insufficient, or the result is unknown, keep the rollout paused, preserve evidence, and escalate to the owner.

Record successful verification after deployment when the observation window is complete and all required signals and behavioral checks meet their criteria. Record recovery when restoration is verified. Record integration, deployment, verification after deployment, and recovery as separate outcomes.
