# 6.4 Pushes and pull requests

A direct push to an integration target is a [target update](../3-workflow/3.8-integration-and-completion.md): complete trusted full checks on the exact combination first. Task-branch quick checks cannot substitute.

## Push authorization

Use a one-time approval for the exact candidate or a valid standing project grant. The authorized owner records the repository, allowed push destination and target ref, responsible role, eligible changes, conditions and how to revoke the grant. Project policy and Git remote configuration alone grant no authority. A one-time approval covers only the checked repository, candidate and stated unverified scope.

On each push, check the outgoing commits, effective push destination, target ref, and applicable authorization. Follow narrower task restrictions. Stop the write if authorization is unclear or out of scope, or the host denies permission. Routine branch push authorization does not cover tag publication, release or deployment.

After pushing, read back the same target ref and verify its SHA at the effective push destination. On rejection, compare local and remote changes without falling back to a force push. If the outcome is unknown, query the original ref before deciding whether to retry.

## Pull requests

For remote collaboration, use a focused PR describing the problem, changes, actual verification, and unresolved limits, with task links where useful. Review the full diff first. A draft PR may request early feedback on incomplete work; mark it ready when applicable checks and preparation are complete. PR creation, comments, and external sends remain subject to existing authorization; this chapter does not trigger them automatically.

Follow the project's PR requirements. After PR approval, verify authorization for applicable merge, installation and release actions. A one-time merge approval covers only the checked repository, candidate and stated unverified scope. Every authorized action still needs its applicable checks.
